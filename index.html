// PROMPT-INJECTION DETECTION · MEASURED, NOT CLAIMED · RUNS IN YOUR BROWSER

A security library that inspects text heading for an LLM and returns an explainable verdict on whether it is a prompt-injection or jailbreak attempt. Prompt injection is the top entry in the OWASP Top 10 for LLM Applications and it is unsolved, so most published guards ship a wall of patterns with no measurement attached. This one ships an evaluation harness and publishes the number that does not flatter it.

Paste anything into the demo below. It runs entirely in your browser, so nothing you type is sent anywhere. That claim is measured: typing produces zero network requests after load.
Live demo, embedded. Open full size
What it does
  • Reports the honest number: 1.000 F1 on the corpus it was tuned against, and 0.350 recall on a held-out set it has never seen. The README leads with the second one, because a perfect score on your own test data measures fit, not skill.
  • Explains every verdict: each result carries the detectors that fired and the exact text they matched, highlighted in place, so a decision can be argued with rather than trusted.
  • Survives obfuscation: a normalization pass folds leetspeak, homoglyphs, zero-width characters, separator padding and letter spacing back to canonical text before matching.
  • Written twice, kept in sync: the guard exists in Python and TypeScript, and a parity test runs the same corpora through both in CI, asserting identical metrics. Duplication becomes verified agreement rather than drift.
  • Names its own blind spots: paraphrase, non-English and social-engineering attacks get through, and the README says so instead of hiding it.

// A MANAGER MODELLED ON YOU · TEN SPECIALIST WORKERS · GUARDRAILS IN CODE

A multi-agent team that runs on your own machine. You give one directive; a manager agent modelled on you turns it into a dependency graph of tasks and hands them to ten specialist workers. Every safety property is a precondition in code rather than an instruction in a prompt, because a model can decline to follow a prompt. Runs fully offline at zero cost, with a defined path to a cloud host once it has earned one.

What it does
  • Plans, then executes: one directive becomes a validated task graph with cycle detection and a closed set of ten worker roles. An illegal plan is rejected by code, not corrected by a prompt.
  • Survives a crash: the queue hands out work under lease, so a killed worker's task returns to the queue instead of vanishing.
  • Fails closed on private data: anything marked personal is pinned to a local model, and an egress tripwire inspects the actual bytes before any outbound request leaves.
  • One live truth: the knowledge store keeps exactly one live statement per subject, enforced by a partial unique index, so it can never hold two contradictory beliefs about you.
  • 55 offline tests, each written against a bug that was reproduced first, including a queue deadlock that reported itself as idle.

// QUALIFIES THE LEAD, BOOKS THE CALL, INSIDE THE CONVERSATION

An AI appointment setter that qualifies inbound leads in a chat window and books the call in the conversation itself, with no calendar link to bounce anyone out to. One workflow serves any number of businesses: each client's persona, offer, and pricing is a database row, so onboarding another is an insert rather than a copied workflow.

Four decisions that make it work
  • The model returns state, not prose. Every reply satisfies a contract of reply, booked, and slot, so booking detection is a code path rather than an interpretation, which is what makes the numbers trustworthy.
  • A deterministic fallback covers model failure. If the provider errors or returns something unparseable, a rules-based reply still goes out. A lead is never left on read because an API had a bad minute.
  • The reply is sent before anything is written, so database writes never add latency to a live conversation.
  • An unknown client is an error, not a default. History is read on client and lead together, so two businesses can never see each other's threads even when the same person messages both.

// SELF-HOSTED n8n · DEPLOYED THROUGH ITS OWN API · PLUS MAKE

I run my own n8n rather than renting one, in Docker, community edition, at zero cost. The part worth hiring is how I build on it: I author workflow JSON and create, patch, and audit it through n8n's REST API, so a workflow is a reviewable file rather than a thing someone clicked together and cannot reproduce. Alongside it, a Make scenario handles lead routing into Google Sheets, Slack, and Airtable.

What I actually run
  • Self-hosted n8n in Docker, community edition, data persisting in a named volume so stopping the container loses nothing. My instance, my data, no per-task pricing.
  • Workflows deployed over the REST API, not assembled by hand. Authored as JSON, pushed, activated, and audited programmatically, which makes them diffable and repeatable.
  • Credentials attached at push time from a node-to-credential map, because n8n's export omits credentials entirely and a naive push silently strips them off every node. That one cost me a broken deploy before I understood it.
  • An error workflow on everything: any failure emails the workflow, the failed node, and a link to the exact execution. Silent failure is the thing I design against.
  • Make scenario for lead routing: a webhook receives an enquiry, branches it, and fans out to Google Sheets, Slack, and an Airtable base whose formula field scores each lead on arrival.
